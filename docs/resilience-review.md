# Нагрузка и отказы — 26 октября 2026

Проверен код приложения `64f745d`. Среда: macOS arm64, Go 1.27.0,
PostgreSQL 16.14, сервер собран с `-race`, пул — 16 соединений.
API, клиент и отдельная PostgreSQL выполнялись на одной машине;
БД использовала Unix-сокет, HTTP — loopback.

Воспроизведение:

```bash
python3 tests/stress/run.py --requests 1000 --concurrency 64 --duration 30
```

Машинные результаты: [resilience-results-2026-10-26.json](resilience-results-2026-10-26.json).
Все 20 проверок в этом файле прошли. Также прошли HTTP E2E, Go-тесты с `-race`
и настоящей PostgreSQL, `go vet`, GolangCI-Lint и проверка синтаксиса OpenAPI YAML.

## Найденный и исправленный дефект

На исходном коде `40ea961` при 32 параллельных клиентах, 300 созданиях PR
и 300 изменениях активности пользователей семь созданий вернули `500`.
Причина в логах — исчерпание трёх повторов конфликта сериализации `40001`.
Нарушений проверенных инвариантов данных не обнаружено.

Исправление: до пяти попыток с экспоненциальной задержкой и случайным разбросом,
суммарная плановая задержка менее 300 мс. При продолжающемся конфликте возвращается
`503 SERVICE_UNAVAILABLE` с `Retry-After: 1`. Эта ошибка означает откат операции;
клиент может повторить запрос. Другие ошибки БД не повторяются автоматически.
HTTP-контракт и README обновлены.

Детерминированные регрессионные тесты проверяют успех после четырёх конфликтов,
отсутствие частичных записей после пяти конфликтов, сохранение SQL-причины,
отмену во время повторов и HTTP 503 для create/merge/reassign.

## Результаты нагрузки после исправления

64 параллельных клиента; всего 117 513 запросов в нагрузочных фазах,
не считая E2E, подготовки данных и запросов отказных сценариев.

| Фаза | Запросы | Результат | p95, мс | p99, мс |
|---|---:|---|---:|---:|
| Создание разных PR | 1 000 | 1 000 × 201 | 36,88 | 53,05 |
| Чтение назначений | 1 000 | 1 000 × 200 | 22,86 | 29,84 |
| Слияние разных PR | 1 000 | 1 000 × 200 | 25,09 | 33,39 |
| Непрерывные create/read/merge, 30 с | 113 721 | 37 907 × 201, 75 814 × 200 | 27,77 | 49,91 |
| Создание PR одновременно со сменой активности | 600 | 300 × 201, 300 × 200 | 76,44 | 106,04 |

В непрерывной фазе получено около 3 785 запросов/с. Под нагрузкой не было
неожиданных ошибок; ответ 503 в этом прогоне не потребовался.
Ветка исчерпания повторов проверена отдельными регрессионными тестами.

По 64 запроса проверили конкурентное создание одного PR, замену одного
ревьювера и повторный merge. Создание и замена дали ровно один успех и 63
ожидаемых конфликта 409. Все merge вернули одинаковый `mergedAt`.
Проверка БД не обнаружила назначения автора самому себе, более двух ревьюверов
на PR или слитых PR без времени слияния. Race detector не сообщил гонок.

## Результаты отказных сценариев

| Условие | Проверенный результат |
|---|---|
| Таблица PR удерживается эксклюзивной блокировкой | Через 25,007 с получен JSON `504 GATEWAY_TIMEOUT` |
| Соединение принудительно оборвано после INSERT PR, перед INSERT ревьюверов | Ответ 500; ни PR, ни назначения не сохранились; повтор создания вернул 201 |
| PostgreSQL аварийно остановлена | `/healthz` — 200, `/readyz` — 503; чтение вернуло 500 примерно за 2 мс |
| PostgreSQL запущена вновь | Тот же процесс API восстановился: readiness 200, создание PR 201 |
| SIGTERM при запросе, ожидающем освобождения БД | После снятия блокировки запрос завершился с 200; API вышел с кодом 0 за 1,181 с |

Ожидаемые 500 во время принудительного обрыва и недоступности БД учитываются
отдельно от ошибок обычной нагрузки. Временные процессы остановлены после проверки.

## Границы вывода

Это локальный прогон, а не установление предельной пропускной способности или SLA.
Клиент также влияет на результат; нет отдельной сети, TLS, балансировщика и
распределённых экземпляров API. Не проверялись многочасовая нагрузка, исчерпание
диска, сетевые разделения, failover реплики, потеря подтверждения COMMIT и
восстановление из резервной копии. Отсутствие ошибок в выполненных сценариях
не доказывает отсутствие остальных дефектов.
